# Deploying the shop for nothing

Frontend on Vercel, backend and database on one Oracle Always Free VM. Costs
nothing, and the two are wired together by a route handler rather than by CORS.

```
Browser ──https──> shop.vercel.app                    Next.js on Vercel
                     │
                     │  /api/*  — same origin, always
                     ▼
              app/api/[...path]/route.ts              forwards server-side
                     │
                     │  http://<vm>:5000
                     ▼
                  Express API                         on the VM
                     │
                     ▼
              /data/usersdb.sqlite                   on the VM's volume
```

## Why there is a proxy in the middle

Because the session token lives in the `shopy-token` cookie, which is
`httpOnly`. JavaScript cannot read it, so a direct browser-to-backend call sends
no `Authorization` header. In development that is invisible — `localhost:3000`
and `localhost:5000` are the same site, so the browser attaches the cookie by
itself. Deploy them to two different domains and it stops being the same site,
the cookie is dropped as third-party, and **every authenticated call answers
401**. Nobody can work around it in the client, because `httpOnly` is the whole
point of `httpOnly`.

`app/api/[...path]/route.ts` forwards the call from the server, where reading an
`httpOnly` cookie is no obstacle at all. Three problems go away at once:

- the token stays out of reach of scripts, and still reaches the backend;
- the browser only ever sees one origin, so no CORS and no cross-site cookies;
- `BACKEND_API_URL` is never read by client code, so it needs no `NEXT_PUBLIC_`
  prefix and cannot be leaked into the browser bundle.

The handler is used in development too, deliberately. Dev then behaves exactly
like production, which is the only way "works on my machine" stays meaningful.

## 1. The Oracle VM

Sign up, then create:

| | |
|---|---|
| Shape | `VM.Standard.A1.Flex`, **2 OCPU / 12 GB** |
| Image | Ubuntu 24.04 |
| Networking | keep the VNet and the autogenerated public IPv4 |
| Boot volume | keep the default (~50 GB of the 200 GB free allowance) |

Two things that cost money if you miss them:

- **"Out of capacity"** is the normal first response for A1 in a busy region.
  It is not a fault in your account — try another region or another time.
- Oracle halved the A1 allowance to 2 OCPU / 12 GB in June 2026. Anything telling
  you to provision 4 OCPU / 24 GB is out of date and will either be rejected or
  will start charging you for the difference.
- Do **not** add a second instance. The free allowance is a total of hours across
  all instances, and one always-on box already uses nearly all of it.
- Do **not** buy a reserved public IP. The ephemeral one included with the
  instance is free; reserved ones are billed.

Outbound data is also billed. A small shop is nowhere near the free egress
allowance, but nothing here should be proxying video.

## 2. The backend on the VM

```bash
sudo apt update
sudo apt install -y git docker.io
sudo systemctl enable --now docker

# Copy the catalogue up rather than starting empty: nothing in scripts/ creates
# products, so a fresh database is a shop with nothing in it. It is 300 KB.
scp E:\Documents\shopify-back\usersdb.sqlite user@<vm-ip>:~/

cd ~/shopify-back    # the backend is its own repository now
docker build -t shop-api .

docker volume create shop-data
docker run -d --name shop-api --restart unless-stopped \
  -p 5000:5000 \
  -v shop-data:/data \
  -e PORT=5000 \
  -e DATABASE_PATH=/data/usersdb.sqlite \
  -e FRONTEND_URL=https://shop.vercel.app \
  -e AUTH_PROVIDER=phone \
  -e TOKEN_KEY="$(openssl rand -base64 48)" \
  shop-api

# put the real catalogue on the volume
docker cp ~/usersdb.sqlite shop-api:/data/usersdb.sqlite
docker exec shop-api chown node:node /data/usersdb.sqlite
docker restart shop-api
```

Check it:

```bash
curl -i http://localhost:5000/api
curl -s http://localhost:5000/api/products | head -c 200
```

If `docker build` fails on sqlite3 that is the one stage worth reading twice: the
compiler is installed there precisely so it cannot, and `--build-from-source` is
set so the build does not quietly depend on GitHub's release CDN being reachable
from your VM.

`TOKEN_KEY` is generated on the spot and **not written down anywhere you will
find it again**. Get the running value and store it in a password manager:

```bash
docker exec shop-api printenv TOKEN_KEY
```

Losing it signs everybody out. Leaking it lets anyone mint a session for any
account. The repository's `TOKEN_KEY=my_secret_key` is a placeholder that must
never reach the internet.

## 3. Open the port

Oracle's default security list allows only port 22.

```bash
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 5000 -j ACCEPT
sudo netfilter-persistent save
```

Only needed while the shop talks to the VM directly, which is the state you are
in now. Once you put TLS in front, tighten this again — see step 5.

## 4. The frontend on Vercel

Push the repository, import it, and set **one** environment variable:

```
BACKEND_API_URL=http://<vm-ip>:5000
```

That is the whole configuration. Do not put `TOKEN_KEY` on Vercel — only the
backend verifies tokens, and giving a second machine the signing key doubles the
blast radius for no benefit.

Deploy. Then check the proxy end to end:

```
https://shop.vercel.app/api/products     → the catalogue, as JSON
```

If that 404s or 502s, the problem is `BACKEND_API_URL`; the handler is working
either way, because a 502 with `UPSTREAM_UNREACHABLE` is the handler reporting
that it could not reach the backend.

## 5. TLS and a domain, once you have one

Talking to the VM over plain HTTP works, but the token crosses the network in the
clear and every visitor sees a warning. Do not leave it there.

Point an `api.` record at the VM and put Caddy in front. Caddy gets and renews a
certificate on its own, which is the entire reason to choose it over Nginx plus
certbot:

```bash
sudo apt install -y caddy
```

`/etc/caddy/Caddyfile`:

```
api.your-domain.com {
    reverse_proxy 127.0.0.1:5000
}
```

Then close the firewall again and let Caddy be the only way in:

```bash
sudo iptables -D INPUT -p tcp --dport 5000 -j ACCEPT
sudo netfilter-persistent save
```

And set `BACKEND_API_URL=https://api.your-domain.com` on Vercel, then redeploy.

Steam sign-in needs this step before it can work at all — see
`docs/steam-auth-cutover.md`.

## 6. Backups

An unbacked-up database on the same disk that can fail is not backed up.

```bash
docker exec shop-api sqlite3 /data/usersdb.sqlite \
  ".backup '/data/backup-$(date +%F).sqlite3'"
```

in cron, daily. `.backup` rather than `cp`: it is the only copy of a live SQLite
file that cannot come out torn.

Keep them for a week and delete them as you go, or the volume fills.

The part that actually protects you is getting a copy **off** the VM — Oracle
Object Storage has a 10 GB free tier, so one nightly upload is enough. A backup
sitting on the disk that is failing is a comment about the disk, not a backup.

## Things that will cost money if you are not careful

| | |
|---|---|
| A second VM instance | The free allowance is hours *across all instances*. |
| A reserved public IP | Billed. The included ephemeral one is free. |
| Outbound traffic | Billed past the free egress allowance. |
| Boot volume above ~50 GB | 200 GB total is free across all volumes. |
| Vercel Pro | Not optional once you take a payment — see below. |

## Vercel Hobby and taking payment

Hobby is **non-commercial only**. Vercel's own fair-use policy counts "any method
of requesting or processing payment from visitors" and "advertising the sale of a
product" as commercial, and pauses accounts that use it that way. It does not
bill you; it takes the site down.

That is fine for as long as you are building. The moment you take the first
payment, the frontend needs Pro at $20/month. Nothing on the backend side ever
costs anything.

## Rolling back

- **Steam sign-in**: set `AUTH_PROVIDER=phone` and restart. The phone flow is
  preserved intact in `routes/legacyPhoneAuth.js`.
- **The proxy**: delete `app/api/[...path]/route.ts` and set every helper's base
  back to the absolute backend URL. Not needed — the proxy works in development
  too, so there is nothing to roll back between environments.
- **The whole backend**: the container is stateless apart from `/data`, so
  redeploying a previous image loses nothing.
